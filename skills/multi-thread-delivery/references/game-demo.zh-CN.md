# 个人游戏 demo 开发参考

本参考补充协作流程中的游戏专用决策；只在本次任务涉及游戏设计或实现时读取。
先判断用户要启动开发、迭代现有工程，还是只做设计；设计请求不自动授权实现。

## 确定有限可玩闭环

- 用一句话定义玩家做什么、得到什么反馈，以及本轮何时结束。
- 约定进入游戏、执行核心动作、观察结果、完成或失败、再次尝试的可玩路径。
- 按玩法选择结束条件；探索、叙事和沙盒 demo 不必硬加胜负或战斗。
- 明确目标设备、输入方式、预期体验、交付形式，以及本轮不做的内容。
- 验收以可观察的行为和交付物为准，不以资源数量或开发时长代替完成条件。
- 玩法扩展进入后续建议；达到本轮约定条件后交付，不自行延长开发。

## 先建立灰盒，再接入正式资源

1. 用简单形状、占位场景和临时反馈验证核心操作及完整闭环。
2. 调整 3C：角色（Character）、镜头（Camera）、控制（Controls）之间的配合。
3. 检查移动、视角、输入响应及必要的交互提示；提示应说明当前可做的动作。
4. 让关键动作有可辨认的视觉和声音反馈，并核对反馈与实际结果一致。
5. 核心玩法成立后再接入正式美术、动画、音效与界面，复核可读性和操作手感。

声音不可用时仍应能理解关键状态；反馈强度与用户选择的风格、平台相适应。
美术可在灰盒阶段并行探索风格与规格，避免在玩法尺寸未定时批量制作最终资产。
仅当闭环需要对手时开发对手 AI，行为复杂度由实际玩法决定。
需要对手时先验证必要的感知、行动和失效处理；无对手的玩法不默认加入敌人系统。

## 引擎、环境与协作职责

尊重用户选定的引擎和版本，沿用可用工程；Godot 只是可选示例，不是默认要求。
引擎尚未确定时，结合目标平台、现有资产和用户经验提出有限选择，再落实实现方案。
先检查现有工具；只有构建、导入或导出确有需要时才处理缺失依赖。
安装依赖须符合本次授权；缺少必要权限时说明具体依赖、用途与受影响交付。
不因启用 Skill 就安装软件、修改全局设置或重建项目目录。

| 默认职责 | 游戏 demo 中的结果与边界 |
| --- | --- |
| 01 统筹与设计 | 定义玩法闭环、体验目标、资源契约和本轮验收；维护当前状态。 |
| 02 实现与集成 | 实现操作、场景与玩法，拥有约定的公共入口，接入专业产物。 |
| 03 专业产物 | 制作本轮需要的美术、动画、音效或 UI；交付规格与来源说明。 |
| 04 验证与交付 | 验证体验路径、回归风险与实际交付物，记录证据和限制。 |

四项是职责映射，不要求创建四个窗口；小改动可以由当前任务承担。
复用属于当前项目的现有任务；仅在用户明确要求时创建缺失的用户可见任务。
内部有限工作可交给可用的子代理；仍须明确文件归属、输入基线及验收条件。
沿用现有目录，资源作者与集成人分别拥有约定文件，避免同时修改公共场景或导入配置。

## 在正式资源制作前约定接口

根据 2D、3D 与资产类型填写相关字段；不适用项可省略，变更时通知接入方。

| 字段 | 需要达成的约定 |
| --- | --- |
| 位置与版本 | 现有目录中的源文件、运行时文件、命名及适用的接口修订。 |
| 坐标与单位 | 世界轴向、角色朝向，以及像素、世界单位或物理尺寸之间的关系。 |
| 尺寸与原点 | 可见范围、缩放、枢轴或锚点；区分画布留白与实际角色边界。 |
| 碰撞归属 | 谁定义碰撞体、触发区和命中区域，是否由代码或场景维护。 |
| 动画与状态 | 状态名称、循环方式、切换条件和必要事件；不依赖未约定的帧序。 |
| 格式与导入 | 文件格式、透明通道、过滤与压缩需求，以及导入配置的负责人。 |
| 音频与界面 | 触发时机、循环或中断规则、布局约束，以及平台需要的适配范围。 |
| 来源与使用 | 原创、生成或第三方来源；记录实际适用的许可与使用限制。 |

资源替换完成后检查比例、朝向、遮挡、碰撞和提示位置，不能只检查文件能否打开。
共享导入缓存或同一编辑器会话产生真实冲突时串行操作；其他独立工作可继续。

## 分层验证实际交付物

- 源工程：检查可加载性、资源引用、运行错误和修改涉及的关键行为。
- 可玩体验：走通约定闭环，核对输入、镜头、提示、反馈及必要的重试或退出路径。
- 导出产物：若本轮要求导出，运行实际生成的包并核对启动、资源、输入和目标环境行为。
- 交付说明：给出真实入口、操作方法、版本或基线、已验证范围及尚存限制。

源工程运行通过不等于导出包通过；无界面检查也不能代替手感与视听体验检查。
只有实际执行过的检查才能标为已验证，无法运行的环境应明确标为未验证。
验收期间固定候选输入；新改动或失败出现后，只重验受影响的范围与相关风险。
遵守现有发布授权，分别报告本地完成、导出完成和外部发布状态。

## 可复制的请求示例

新项目启动（填写占位内容后使用；以下请求明确授权创建缺失任务）：

> 使用 $multi-thread-delivery 启动 [游戏类型] 的有限可玩 demo，目标是 [核心闭环]，引擎为 [用户选择]，工程位置为 [项目位置]。先检查工程与当前项目任务；复用相关现有任务，为可独立推进且尚无负责人的工作创建缺失的独立任务。按统筹、实现、专业产物、验证交付分配职责，可按实际工作合并。先灰盒，再按接口接入资源；沿用目录。交付 [源工程或导出目标]，以 [可观察完成条件] 收口。安装、覆盖和外部发布仅限我已经授权的范围。

现有 demo 迭代：

> 使用 $multi-thread-delivery 继续当前 demo，只完成 [本轮变化]。复用现有任务，不创建新任务窗口；保留本轮之外的玩法和现有目录。先核对当前基线与资源接口，验证受影响的可玩路径，交付结果与限制。

只做设计：

> 使用 $multi-thread-delivery，为 [玩法设想] 设计有限 demo 的闭环、灰盒范围、职责分工和资源接口。只交付设计建议，不创建任务、不改工程、不安装软件，也不启动开发。
