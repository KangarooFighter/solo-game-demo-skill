# 工具适配与权限边界

执行任务协调或恢复前读取。本文件是能力路由，不是固定 API schema；以当前会话实际工具描述、平台规则与用户指令为准。工具缺失时如实说明，不伪造发送或完成记录，不为补齐协作能力安装未请求的插件。

## 用户可见任务和内部子代理

| 目的 | 能力路由 | 注意点 |
| --- | --- | --- |
| 复用已有用户任务 | list_threads → 必要时 read_thread | 查项目、host、cwd、状态；向用户引用真实标题，不把摘要当标题 |
| 明确要求创建用户任务 | list_projects → create_thread | 当前任务可承担统筹，避免多建一个；只创建确实缺少的角色 |
| 给已有任务继续派工 | send_message_to_thread | 消息是可见工作指令，不是聊天通知总线；别只发无动作的“收到” |
| 有限并行子任务 | collaboration.spawn_agent／followup_task 等可用能力 | 委派具体可独立完成的工作，主任务同时做有用工作；不当作已经创建独立用户窗口 |
| 等待用户任务 | wait_threads | 用已返回的 host、cursor，按工具上限批量等待；需要快照时 timeoutMs:0 |
| 等待内部子代理 | collaboration 的等待／状态能力 | 与用户任务工具分开，不把 agent_id 当 threadId |
| 展示产物 | open_in_codex 或可用预览能力 | 只打开可验证的结果；显示面板不等于已经运行内容 |

创建项目任务时使用 list_projects 的真实 projectId 和 isGitRepository，遵守当前工具对 local/worktree 的默认要求。用户明确选择保存的本地目录时保留该选择。不要发明分支名、起始状态或切到未知分支；需要新分支时遵守环境约定。收到 clientThreadId 表示设置中，不当成 threadId 发消息或等待；等真实ID可解析后再使用。

用户没有明确要求新任务时，可以复用现有任务、用内部子代理、当前任务实现，或仅给出角色建议；不能因为模板写“四职责”就自动创建四个窗口。没有任务工具时交付可复制的任务单，并说明尚未发送，能在当前环境完成的工作继续做。

不在 skill 中写死 Astra 或任何模型。默认保留用户当前配置和已有任务设置；用户指定模型时用当前工具支持的精确名称，不擅自升级、降级或虚报模型已切换。模型／工具权限不通过另一任务绕开。

## 交接、冻结与环境

任务分配的逻辑交接与产品的 handoff_thread 不是同一回事。前者转移某项文件／资源责任；后者可能中断运行任务并移动 Git 工作状态。除非确需且已获相应授权，不为普通任务单交接调用物理 handoff。

共享本地工作区要互斥索引／公共文件与真正共享的运行资源；不同工作树可并行编辑，但不要同时改共同 refs 或发布同一目标。验收必须说明是哪个工作树／合并版本。集成者核对接口与内容，不凭“另一边测试通过”跳过有差异的集成检查。

若需冻结，指定候选与文件范围、允许继续的无关工作、结束条件、后续执行者。停止拥有者后才转移写权限；任务超时或“很久没回”不是已经释放资源的证据。只处置自己拥有、已核实的进程和锁，不关闭用户的无关应用。

## 等待和中断恢复

保存最近游标，收到未变状态时继续适度等待；不要反复 read_thread 全历史或持续发送相同催促。若确有停滞，做一次相关状态／原件检查，发送一条精确恢复或阻塞询问，然后等待变化。原负责人可能仍在执行时不再启动第二个写入者。

长等待遵守当前工具限制，安排短于会阻塞必要沟通的调用。无新状态不需要对用户反复播报“仍在进行”；正常沟通可说明新决策或已验证的局部结果。

调度发送成功只证明平台接受消息；子任务完成回报也不替代关键产物核验。必要时读取原结果、命令外层状态或目标应用。产品不提供的遥测注明不可见，不推断后台运行、窗口焦点或人工体验。

## 自动化和外部发布

仅在用户要求稍后、周期性、持续跟进或监控时，使用产品提供的 automation_update 等能力；先检索同目标既有自动化，避免重复。不要因为“多任务协作”自动安排心跳，不用 shell sleep/cron 伪装持续后台能力。继承平台的通知与停止规则，不能承诺关机、权限缺失时仍能运行。

本 skill 的“01许可／条件交接”只表示在用户已授权范围内协调，不是用户授权的替代品。远程地址、发布可见性、覆盖目标、安装范围等未明确时，先完成不依赖它们的在范围内工作，在需要新权限前停下说明。持续工作或“不提问”不扩大这些权限。
